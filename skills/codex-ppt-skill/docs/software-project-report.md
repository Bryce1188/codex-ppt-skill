# 软件项目工作汇报

用于功能演示、技术架构、数据库设计和项目进展汇报。先判断听众：负责人主要关心完成了什么、证据、问题与下一步；技术评审需要额外解释实现选择。不要把完整开发文档压缩成一套图片。

## 先核对项目版本

实际读取入口、依赖、数据访问代码、数据库建表或迁移文件，再使用 README 和旧设计文档。发现冲突时记录各自版本，以本次要汇报的实现为准；不能拼接两套技术栈。文件名也不是图类型的证据：先看图，再判断是用例图、ER 图还是类图。

区分代码存在、界面可打开、演示数据、数据库操作实测、性能测量。截图显示一个按钮，不代表该操作已通过测试。无数据库时可使用项目原有演示模式并标注；不要为截图导入或重置业务数据库。

## 按内容制作三类代表页

| 页型 | 内容与构图 | 必须检查 |
| --- | --- | --- |
| 功能 | 一个具体用户任务、一张大截图、少量解释。可从“选择板块、阅读帖子、回复讨论”中挑一个主要场景。界面通常占页面约六成，按可读性调整 | 原图比例和关键控件可读；演示状态、角色和数据来源明确；不把多张整屏图缩成邮票 |
| 架构 | 一条主要请求路径，加确有依据的事件或异步支路。节点写名称、职责和技术；箭头标调用含义 | 从调用方指向被调用方，推送指向接收方；区分逻辑模块、进程、部署节点；省略响应时说明 |
| 数据库 | 选择支撑一个业务流程的核心表，保留 PK、FK、基数、可空性及与讲述有关的约束。全库模型可放附录 | 关系来自 SQL/迁移；不要按字段名称猜外键；明确是核心子集；父子两侧基数与可空性一致 |

默认把技术图画成原生形状、文字和附着连接线。关系可以简化展示，但必须说明省略范围；不能把图片式 ER 图称为可编辑图示。构建器支持的几何与连接方式见 [可编辑构建](editable-production.md)。

同一套稿可让功能页以图片为主、架构页以关系为主、数据库页以字段为主。通过相同字体、主题色和对齐基准保持统一。不要让三个页面只在标题和配色上有所区别。

## 试做后再批量展开

1. 从用户参考或实际公开案例提取构图、字级、图像比例及标注方法，记录可借鉴之处，不复制第三方模板资产。
2. 用当前项目的功能、架构和数据库内容试做代表页；任务不涉及某类内容时不强行补齐。
3. 从最终 PPTX 渲染并查看。检查标题能否快速找到、关键界面是否可读、箭头是否正确、表关系能否顺着讲解。发现问题后改稿，再渲染。
4. 只有通过上述检查的方法才作为本次全稿的设计规则。客观检查与审美判断分开记录，不用“测试通过”证明设计优秀。

需要比较两种风格时，保持内容相同，改变构图、图像占比、字级或图示组织；只换三种颜色叫配色比较，不叫三种设计方向。

## 背景与文字

功能页通常已有复杂界面，架构和数据库页已有图示，优先用低干扰底色。题材插画适合封面或章节页，不能遮挡结果与连接线。需要生成背景时先按 [背景选择](background-selection.md) 判断用途，再给用户真实样页或局部修改结果。

Humanizer 处理“主体做了什么、有什么证据、还有什么缺口”，删去“全面赋能、显著提升”之类没有依据的评价。保留技术名、指标口径、未测试范围和真实困难。Superpowers 用于补问影响汇报的缺项及组织检查；它不替代截图、排版或渲染工具。
