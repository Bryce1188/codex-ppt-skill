# 可复用的项目汇报版式

先确定这一页要解释什么，再选构图。统一来自共享字级、对齐与图示规则，页面组织随内容变化。可运行源见 [四页示例](../examples/software-report/deck.json)，共用 [项目汇报配置](../references/design-profiles/project-report.json)。

| 要讲的内容 | 构图与内容槽位 | 淘汰条件 |
| --- | --- | --- |
| 功能与操作 | 先给完整界面定位上下文，再裁切放大关键操作；截图编号与旁边注释对应。必要时分总览、细节两页 | 整屏缩小后按钮读不清；注释离控件太远；编号遮挡证据；裁掉失败状态 |
| 总体架构，示例第 1 页 | 调用方、服务、数据存储横向展开；虚线表达真实进程或服务边界；事件支路另走 | 把一次点击的步骤混进架构；同一进程误画成独立部署；连线穿过文字 |
| 一次业务流程，示例第 2 页 | 按输入到结果排列少量步骤；下方解释事务边界、异常或关键处理 | 只有技术名称而没有动作；箭头标签过长断字；补充文字复述节点 |
| 核心数据关系，示例第 3 页 | 保留支撑当前任务的实体、PK/FK、基数与关键约束；下方说明设计理由 | 整库字段挤进正文；外键靠名字猜；只列字段却不解释关系 |
| 方案取舍，示例第 4 页 | 两列使用相同比较维度；写本次选择、依据与代价 | 把假设写成收益；没有实测却宣称更快；两边维度不对应 |

功能细节使用独立图片的原生裁切，保留完整原图和上下文页，参数见 [可编辑构建](editable-production.md)。不得用重绘界面代替真实截图。没有运行界面时，说明缺口，改用有依据的代码路径或设计图。

完成代表页后看完整汇报：目录与正文对应，功能证据、技术解释、结果与后续能顺着讲。若连续页面都只是等宽方框或短词列表，应重新组织内容；不要靠换底色制造变化。按 [最终检查](quality-assurance.md) 查看最终 PPTX，记录具体问题和修改，结构检查不能代替设计判断。
